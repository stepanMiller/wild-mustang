# Wild Mustang

Wild Mustang — браузерная 3D-игра на Three.js, рассчитанная прежде всего на Safari на iPad. Репозиторий также сохраняет каркас проекта Unity 6 LTS.

## Запуск браузерной игры

Игра запускается как статический сайт из корневого файла `index.html`. Для локального запуска поднимите HTTP-сервер в корне репозитория:

```bash
python3 -m http.server 8000
```

Затем откройте `http://localhost:8000` в браузере. Прогресс хранится на устройстве с помощью `localStorage`.

## Публикация в GitHub Pages

Workflow `.github/workflows/pages.yml` автоматически публикует статический сайт из ветки `main`. В настройках репозитория для GitHub Pages должен быть выбран источник **GitHub Actions**.

## Unity-проект

Unity-файлы остаются частью репозитория и могут использоваться независимо от браузерной игры.

## Как открыть проект

1. Установите Unity 6 LTS через Unity Hub.
2. В Unity Hub выберите **Add project from disk**.
3. Укажите корневую папку этого репозитория.
4. Дождитесь импорта пакетов и генерации локальных файлов Unity.
5. Откройте сцену `Assets/Scenes/Bootstrap.unity` как стартовую точку проекта.

## Структура проекта

```text
Assets/
├── Art/          # 2D/концепт-арт и визуальные источники
├── Animations/   # Animation Clips, Animator Controllers, риги
├── Audio/        # Музыка, SFX, микшеры
├── Characters/   # Ассеты персонажей и связанных сущностей
├── Editor/       # Editor-only инструменты Unity
├── Materials/    # Материалы, шейдерные настройки, текстурные пресеты
├── Models/       # 3D-модели и импортируемая геометрия
├── Prefabs/      # Переиспользуемые prefab-объекты
├── Scenes/       # Сцены Unity: Bootstrap, MainMenu, Game
├── Scripts/      # Runtime C# код проекта
├── UI/           # UI ассеты, prefabs, USS/UXML при необходимости
└── Settings/     # ScriptableObject-конфиги и проектные настройки в Assets
```

Дополнительная документация находится в `docs/`:

- `Architecture.md` — предлагаемая архитектура и границы слоёв.
- `Roadmap.md` — краткий шаблон этапов разработки.
- `GameDesign.md` — шаблон дизайн-документа.

## Стартовые сцены

- `Bootstrap` — будущая техническая точка входа: загрузка сервисов, конфигов и переход к нужной сцене.
- `MainMenu` — будущая сцена главного меню.
- `Game` — будущая игровая сцена.

## Правила разработки

- Один этап разработки должен решать одну законченную задачу.
- Коммиты должны быть небольшими, безопасными и понятными.
- Не добавлять игровые механики без отдельной задачи.
- Не смешивать инфраструктурные изменения, геймплей и визуальные правки в одном коммите.
- Любая новая система должна иметь понятную ответственность и документированную точку входа.
- Runtime-код не должен зависеть от `Assets/Editor`.
- Временные Unity-папки (`Library`, `Temp`, `Obj`, `Builds`, `Logs`) не коммитятся.

## Соглашения по именованию

### Файлы и папки

- Папки в `Assets/` именуются в `PascalCase`: `Scripts`, `Prefabs`, `Materials`.
- Сцены именуются в `PascalCase`: `Bootstrap.unity`, `MainMenu.unity`, `Game.unity`.
- Prefab-файлы именуются по назначению: `Horse.prefab`, `MainMenuView.prefab`.
- ScriptableObject assets рекомендуется именовать с суффиксом `Config`: `MovementConfig.asset`.

### C# код

- Типы, методы и свойства: `PascalCase`.
- Приватные поля: `_camelCase`.
- Интерфейсы: префикс `I`, например `ISaveService`.
- Абстрактные базовые классы: осмысленное имя без искусственного суффикса, если контекст очевиден.
- Пространство имён проекта: `WildMustang` и вложенные области по модулям.

## Предлагаемая архитектура

На этом этапе архитектура только описана и не реализована.

Рекомендуемый подход:

- **Bootstrap layer** — единая точка входа приложения, инициализация сервисов, загрузка конфигураций и управление переходами между сценами.
- **Game flow layer** — управление состояниями игры: запуск, меню, загрузка, игровой процесс, пауза, завершение сессии.
- **Feature modules** — изолированные модули будущих фич: персонаж, мир, UI, аудио, сохранения. Каждый модуль должен иметь минимальные публичные API.
- **Domain/data layer** — чистые модели данных и конфиги без зависимости от Unity-сцены там, где это возможно.
- **Presentation layer** — MonoBehaviour-компоненты, UI views, visual/audio bindings.
- **Infrastructure layer** — сохранения, загрузка ресурсов, аналитика, platform services. Внешние SDK должны быть скрыты за интерфейсами.

Код рекомендуется разделять по assembly definitions на более позднем этапе, когда появятся первые реальные модули. До появления потребности asmdef-файлы не создаются, чтобы не усложнять каркас преждевременно.
